## Codebase Patterns
- Testing async SQLAlchemy mocks: For single `session.execute()` calls, use `AsyncMock(return_value=_make_result(...))`. For multiple sequential calls, use `session.execute = AsyncMock()` with `session.execute.side_effect = [result1, result2, ...]` where results are plain `MagicMock` objects (AsyncMock wraps them into coroutine return values automatically). Explicitly set `session.add = MagicMock()` since AsyncMock defaults return CoroutineMocks that don't track sync calls correctly.
- Recovery dashboard pattern: create `GET /recovery/dashboard/{user_id}` combined endpoint returning weak topics + active plans + AI recommendations; frontend page at `dashboard/src/app/recovery/page.tsx` with student selector
- Dashboard page pattern for standalone pages: 'use client', student/user ID selector, fetchWithTimeout, three states (loading/error/data), grid layout with stat cards
- Mastery history tracking pattern: `TopicMasteryHistory` model records a snapshot on every `_update_mastery()` call; history endpoint at `GET /recovery/history/{user_id}/{topic}`; frontend mini SVG line chart in recovery dashboard
- When adding history snapshots, record them in `_update_mastery` (weak_topic_detection.py) for quizzes, and use the `record_mastery_history()` helper for other sources like task completion

- Weak topic detection follows: `analyze_quiz_attempt()` wired into quiz submit endpoint → creates/updates `StudentMastery` and `MisconceptionPattern` records → `_update_student_profile_weak_areas()` syncs `StudentProfile.weak_areas` and `topic_mastery` JSON fields
- New database models for recovery features follow existing patterns: UUID PK, FK to users, timestamps, JSON for flexible fields
- Weak topic analysis is non-blocking (called after XP/streak/achievement logic, before commit)
- When adding analysis to existing endpoints, call analysis functions AFTER gamification logic but BEFORE session.commit()
- The `QuizAttempt.answers` field is `Mapped[dict]` in SQLAlchemy but stores list data — always `cast(list[Any], ...)` when accessing
- RecoveryAgent follows the same BaseAgent._call_llm() pattern as QuizAgent/DiagramAgent, but generates plan data + saves to DB in one call
- AI generation endpoint pattern for recovery: get weak data → build prompt with weak topics → call LLM → parse JSON → save plan+tasks → return
